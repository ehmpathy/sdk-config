# vision: schema-driven optional keys

> ⚠️ **shipped contract narrowed — this approved vision is partly superseded.** the execution
> adopted a simpler *safeParse-arbiter, no-walk* design that narrows two tolerated edgecases
> below (nullable-only `null`-fill; ancestor-optional drop of a required leaf). both now
> hard-throw. the authoritative shipped contract + migration is in
> `5.1.execution.from_vision.yield.md` ("contract narrowings vs the wisher-approved vision").
> this file is kept as the approved record; the ⚠️ callouts inline mark the narrowed spots.
> **needs wisher sign-off** on the two narrowings.

> mark a config field `.optional()` (or `.nullable()`) in the zod schema, and `sdk-config`
> tolerates that field being unreadable (authz-denied or absent) instead of failing fast.
> everything not marked optional stays required — same strictness as today.

---

## the outcome world

### day-in-the-life

a team runs a cicd pipeline split into two oidc-scoped jobs:

- **plan job** — assumes a reader role IAM-denied on every ssm param except `.../grant=plan/*`
- **apply job** — assumes a role IAM-denied on everything except `.../grant=apply/*`

both jobs load the *same* config via the *same* `getConfig()`. today that is impossible:
`asFilledConfig` eagerly fetches every `$.at()` ref and hard-throws on the first denied one.
the plan job explodes trying to read the apply-grant password it is not allowed to touch —
even though it never needs it.

after this wish, each job marks the *other* grant `.optional()` in its schema (driven by
`process.env.GRANT`). the plan job tolerates its AccessDenied on `apply.password`, reads
`plan.password` normally, and `getConfig()` resolves cleanly. the apply job mirrors it.

### before / after

| | before | after |
|---|---|---|
| denied param, field required | throw (correct) | throw (unchanged) |
| denied param, field `.optional()` | throw (wrong — blocks the job) | key omitted, resolves |
| throttle/network on any field | throw | throw (unchanged, never masked) |
| none denied | resolves | byte-identical, no regression |

### the "aha" moment

> "i don't hand `sdk-config` a list of which keys are optional. the schema I already pass
> *is* the list. `.optional()` is the signal."

the value clicks when a restricted role resolves a config it was previously locked out of —
with zero new config surface, no keyPath allowlist, no interpolation.

## user experience

### usecases & goals

- **primary**: a role with partial IAM grants resolves a shared config without seeing errors
  for the params it is legitimately denied.
- **secondary**: a field that is genuinely env-conditional (present in prod, absent in test)
  can be marked optional once and behave correctly across environments.

### contract inputs & outputs

no new surface. the extant `genGetConfig` contract is unchanged for the caller:

```ts
const getConfig = genGetConfig({
  schema,        // ← the only signal; .optional()/.nullable() marks tolerable fields
  statics,
  cache,
  suppliers,
  environment,
  repoName,
});

const config = await getConfig();   // resolves; optional-and-denied keys simply absent
```

the *behavior* of `getConfig()` changes at the fill boundary — internally, `asFilledConfig`
gains the schema so it can ask "is this keyPath optional?" before deciding tolerate-vs-throw.

### what it looks like to leverage it

```ts
// config.schema.ts — env-conditional grant, the ONLY per-repo code
const grant = process.env.GRANT ?? 'apply';
const cicd = z.object({
  username: z.string(),
  plan:  grant === 'plan'  ? z.object({ password: z.string() })
                           : z.object({ password: z.string() }).optional(),
  apply: grant === 'apply' ? z.object({ password: z.string() })
                           : z.object({ password: z.string() }).optional(),
});
```

```json
// config/prod.json — fixed $.at paths, no interpolation
{ "role": { "cicd": {
  "plan":  { "password": "$.at(aws::param)" },
  "apply": { "password": "$.at(aws::param)" }
} } }
```

```yaml
# .sql-schema-control.yml
plan:  { env: { GRANT: plan } }   # apply-grant optional → its denied param tolerated
apply: { env: { GRANT: apply } }  # plan-grant optional → mirror
```

### timeline

1. consumer bumps `sdk-config`, marks the off-grant field `.optional()` from `process.env.GRANT`
2. plan job runs → reader role denied on `apply.password` → tolerated → `getConfig()` resolves
3. apply job runs → mirror → resolves
4. exactly one grant is required per job = true failfast preserved

## mental model

### how a user describes it to a friend

> "zod already knows which fields are optional. sdk-config just started *listening* to that
> when a secret can't be read. required field denied? still blows up. optional field denied?
> it shrugs and moves on."

### analogies

- **a guest list with plus-ones**: required fields are named guests — if one doesn't show,
  the event is broken. optional fields are plus-ones — nice if present, no problem if absent.
- **TypeScript `?`**: `field?: T` at the type level; `.optional()` at the runtime-fetch level.
  the wish makes runtime honor what the type already declares.

### terms

| they say | we say |
|---|---|
| "optional key" | field marked `.optional()`/`.nullable()` in the zod schema |
| "it's allowed to be missing" | keyPath is optional in the derived json-schema |
| "denied but that's fine" | **tolerable error** (AccessDenied / not-found) on an **optional field** |
| "the plan can't touch apply's secret" | authz-denied param outside the role's oidc grant |

## evaluation

### how well it solves the goal

directly. the two constraints the wish demands both hold:

1. **failfast by default** — required + denied still throws, with denied path in context.
2. **tolerate only what's explicitly optional** — optional + tolerable-error → key omitted.

and the safety invariant the peer baked in:

3. **error-class tolerance is orthogonal to field optionality** — *both* must hold to
   tolerate. an optional field can never silently swallow a throttle/outage.

### why this over a two-schema split

the oidc split could be met with **zero sdk-config change**: give each job its own config file +
schema that references only the params its role may read. we choose the shared-config +
schema-optional design instead because **one** config is the single source of truth — two
divergent files invite drift (a param added to one job's config but not the other's is a silent
prod hazard). the feature buys single-source safety; that is the requirement that justifies it.

### pros

- zero new config surface; the schema is the single source of truth
- no keyPath allowlist to maintain or drift
- `keyPath` is *already* threaded through `fillRecursive` — the lookup has its input for free
- json-schema route (`z.toJSONSchema`) avoids brittle zod-internal (`._zod.def`) coupling

### cons

- a subtle behavior: an optional field silently absent could mask a genuine misconfiguration
  (wrong path) that happens to return not-found. mitigated because required fields still throw,
  but optional fields trade strictness for tolerance by design.
- adds a schema→json-schema derivation cost (mitigated by caching once per `getConfig` closure)

### edgecases & pit-of-success

| edgecase | contract behavior |
|---|---|
| `.optional()` field, AccessDenied | key omitted (substitute `undefined`), safeParse passes |
| `.nullable()`-only field, AccessDenied | substitute **`null`** (NOT omit), safeParse passes |
| `.optional().nullable()` / `.nullish()`, AccessDenied | key omitted is safe (both `undefined` and `null` accepted) |
| required field, AccessDenied | throw fast, denied path in context |
| throttle/network, any field | throw (never masked) |
| none denied | byte-identical to today |
| nested: `a.b` optional, required leaf `a.b.password` denied | omit the **whole optional node** `a.b` (not just the leaf) — a present optional node must satisfy its required children |

> ⚠️ **substitution value differs by mark** — `.optional()` accepts absence, `.nullable()`
> accepts `null` but *rejects* absence. so tolerance cannot uniformly "omit the key": a
> nullable-only field must be filled with `null`, else safeParse fails. the wish's "substitute
> undefined and move on" is correct only for `.optional()`. see open question Q4.

## open questions & assumptions

### assumptions

1. **AccessDenied is distinguishable at the fill boundary.** ⚠️ see "what is awkward" — the
   current param supplier does *not* surface AccessDenied distinctly; it treats it as transient
   and rewraps into `MalfunctionError` after retries. the vision assumes we fix classification
   so AccessDenied is a *tolerable* error, distinct from throttle/network.
1b. **only a *persistent* AccessDenied is tolerable.** ⚠️ IAM is eventually consistent — a
   freshly-assumed role can get a *transient* AccessDenied until its grant propagates. the extant
   supplier already retries all non-not-found errors 3x (`genSdkConfigSupplierAwsParameterStore.ts:26,57`).
   so tolerance must run *after* retries are exhausted, never on the first AccessDenied — else we
   drop the retry and mask a transient denial (violating R3's "never mask transient"). see Q6.
2. `z.toJSONSchema(schema)` yields standard json-schema with `required[]` arrays and
   nullable-permitting types for every level we care about. (verified the API exists in zod
   4.3.6; not yet verified its output shape for `.optional()`/`.nullable()` at each nesting.)
3. **[confirmed by wisher]** the fill-time rethrow for required-and-denied should throw **always**,
   independent of `isFailfastEnvironment` (which today only gates *schema-validation* failfast). a
   denied required secret is not "schema drift" to warn-through in prod/cloud — it's a hard failure.

### design implication — "the schema is the final arbiter" (from wisher's Q2 answer)

the wisher's principle ("either conforms to schema or does not") points to a **simpler design than
the wish's pre-fetch optionality walk**:

- on a *tolerable* error (persistent denial / not-found), substitute **`undefined`** and continue —
  **without** first consulting the schema for optionality. then let `safeParse` be the sole arbiter:
  - `.optional()` / `.nullish()` field → accepts `undefined` → **passes** (tolerated)
  - `.nullable()`-only field → rejects `undefined` → **fails** (correct: it is required-present)
  - required field → rejects `undefined` → **fails** (correct: hard non-conformance)

this **removes the need for `z.toJSONSchema` optionality derivation entirely** — which retires
assumption #2 (the single assumption "most likely to be false") and the whole json-schema-walk +
nested-ancestor edgecase machinery. the schema's own `safeParse` already encodes every optionality
rule (optional vs nullable vs required, nested or flat) — so we should not re-implement that logic
by hand.

- **two residual points for the execution stone** (not blockers):
  1. **denied-path context**: `safeParse`'s "field required" message loses the AccessDenied cause.
     to honor "throw hard with the denied path", the fill layer should still *record* which
     keyPaths it substituted-on-tolerable-error, and enrich the validation-failure throw with them.
  2. **prod/cloud throw-hard vs today's warn-on-validation**: today prod/cloud *warns* on a
     safeParse failure. "throw hard for required-denied" means an unreadable *required* secret must
     throw even in prod/cloud — stronger than schema-drift warn. the execution stone must
     distinguish "absent because denied" (throw hard, always) from "present but wrong" (extant
     warn-in-cloud), via the substituted-keyPath record from point 1.

net: adopt the safeParse-arbiter model; keep only a lightweight record of tolerable-substituted
keyPaths to (a) enrich errors and (b) force hard-throw on required-denial. this is smaller, safer,
and directly honors "the schema is the final requirement".

### open questions (triaged)

each question is tagged `[answered]` (settled now via zod logic / code read), `[research]` (verify
in the execution research phase), or `[wisher]` (only the wisher can decide the policy).

- **Q1 [answered]** — optional field omitted, schema gives it a `.default()`: does the default
  apply? **yes.** zod applies `.default()` whenever the parsed value is `undefined`; an omitted
  optional key is `undefined`, so the default fires. this is the intended fallback — no special
  step needed, and it is correct behavior.
- **Q2 [answered — wisher]** — required-and-denied: throw hard, or degrade to warn? **throw hard.**
  the wisher confirmed: "the schema is the final requirement; either conforms to schema or does
  not." a required field that cannot be filled means the config does not conform → hard failure,
  same strictness as a required field absent today. (see the design implication below.)
- **Q3 [answered]** — should a *required* denied field keep today's exact `BadRequestError`
  message, or unify? **unify under the tolerable-error taxonomy** (awkward #1): required-denied
  rethrows a typed error that carries the denied `path` + `hint`. no acceptance test asserts the
  supplier's "parameter not found" string on a fill path (the one snapshot,
  `index.acceptance.test.ts` case2, asserts the *schema-validation* message), so the exact legacy
  string is not a contract — an execution detail.
- **Q4 [answered]** — substitution rule by mark: **`.optional()` ⇒ omit / `undefined`;
  `.nullable()`-only ⇒ substitute `null`; `.optional().nullable()` / `.nullish()` ⇒ omit safe.**
  settled by zod semantics (see edgecase table + ⚠️ callout above); no wisher input needed.
- **Q5 [answered]** — required leaf under an optional ancestor denied: omit the whole optional
  ancestor (which drops readable siblings)? **yes, necessarily** — a *present* optional object must
  satisfy all its required children, so a partial fill fails safeParse; the node is all-or-none.
  settled by zod logic.
- **Q6 [answered]** — tolerate only a *persistent* AccessDenied (after retries), never the first?
  **yes** — IAM eventual-consistency can make AccessDenied transient, and the suppliers already
  retry 3x; tolerance must sit at the post-retry seam so a transient denial is never masked. this
  is decided by R3's safety invariant, not a preference; wisher confirmation is a courtesy only.

### must research externally `[research]`

- **[research]** `z.toJSONSchema` output for `.optional()` (expect: key absent from parent
  `required[]`), `.nullable()` (expect: `type: ["string","null"]` or `anyOf` with null), and edge

  the single assumption most likely to be false — see assumption #2.)*
- **[research]** AWS SDK v3 error identity for authz denial: `AccessDeniedException` (`error.name`)

## groundwork

### external research

- **zod 4.3.6 `z.toJSONSchema`** — verified the export is present:
  `node_modules/zod/v4/classic/external.d.ts:9` (`export { toJSONSchema } from "../core/json-schema-processors.js"`).
  Not yet verified its *output shape* for nested `.optional()`/`.nullable()` — flagged as Q above.
- **AWS SDK error classes** — `ParameterNotFound` is imported and handled today in
  `genSdkConfigSupplierAwsParameterStore.ts:4,45`. `AccessDeniedException` is **absent** from
  the codebase — no reference anywhere — confirming assumption #1's gap.

### internal research

extant behavior this wish extends (verified, with cites):

- **`genGetConfig`** (`src/domain.operations/genGetConfig.ts:16-98`) — already holds `schema`
  and calls `asFilledConfig` at line 45-50. threading schema in is a one-arg change. contract:
  returns `getConfig` with `.static()` / `.filled()`.
- **`asFilledConfig` / `fillRecursive`** (`src/domain.operations/asFilledConfig.ts:15-107`) —
  `keyPath` is **already** computed and threaded (lines 80, 91-97). the sole supply call to wrap
  in try/catch is line 68 (`supplier.supply({ path })`). this is the exact seam the wish names.
- **`SdkConfigSupplier`** (`src/domain.objects/SdkConfigSupplier.ts:5-15`) — contract is
  `{ scheme, supply({ path }) => Promise<string> }`. errors propagate from `supply`.
- **param supplier** (`src/domain.operations/genSdkConfigSupplierAwsParameterStore.ts:23-67`) —
  rewraps `ParameterNotFound` → `BadRequestError` (line 48); every other error is retried then
  thrown as `MalfunctionError` (line 61). **AccessDenied currently lands in the retry path.**
- **secrets supplier** (`src/domain.operations/genSdkConfigSupplierAwsSecretsManager.ts:23-77`) —
  structurally symmetric BUT **not** identical: not-found is `ResourceNotFoundException` → rewrapped
  `BadRequestError('secret not found')` (lines 50, 54); other errors retried → `MalfunctionError`
  (line 70). so the two suppliers use *different* not-found identifiers and messages, and **both
  erase the original AWS error class before fill sees it** — AccessDenied reaches fill only as a
  post-retry `MalfunctionError`, never as `AccessDeniedException`.
- **`isFailfastEnvironment`** (`src/domain.operations/isFailfastEnvironment.ts:14-30`) — governs
  *schema-validation* failfast only. the new fill-time tolerate-vs-throw is a **separate** concern.
- **vocab to reuse**: `keyPath` (dot-delimited), transformer verbs `as*`/`is*`/`gen*`,
  `choice: EnvironmentConfigSlug`. a new classifier reads naturally as e.g.
  `isTolerableSupplyError({ error })` and `isOptionalKeyPath({ jsonSchema, keyPath })`.
- **stdout/error shape**: `BadRequestError` / `MalfunctionError` from `helpful-errors` with a
  `hint` field — the required-and-denied rethrow should preserve the denied `path` + a `hint`.

## what is awkward?

1. **the error-identity-erasure gap (biggest).** the wish's contract pivots on "AccessDenied is a
   *tolerable* error" and says fill should classify by the AWS class (`AccessDeniedException`). but
   **both** suppliers rewrap their errors before fill ever sees them: not-found → generic
   `BadRequestError` (with *different* messages per scheme: "parameter not found" vs "secret not
   found"), and AccessDenied → post-retry `MalfunctionError`. so the AWS class is **gone** at the
   fill boundary — the wish's "classify by `AccessDeniedException`" is not implementable as written.
   the real fix is larger than the wish's `.change` list: introduce a **structured
   tolerable-supply-error taxonomy** (e.g. typed `SupplyDeniedError` / `SupplyAbsentError`) that
   *both* suppliers throw and fill reads, raised *after* retries so a transient denial is never
   masked. this spans both supplier files, not the two the wish names.

2. **required-vs-optional lives in the schema; tolerable-vs-transient lives in the supplier.**
   the decision needs *both* facts at the *fill* layer — which means fill must reach across two
   abstractions (schema optionality + supplier error identity). clean seam, but it couples fill
   to error taxonomy it didn't previously care about.

3. **json-schema as the optionality oracle.** deriving json-schema to answer "is this keyPath
   optional?" is robust across zod minors, but it's an indirection: the *authoritative* zod
   schema is translated to a *lossy* json-schema just to walk `required[]`. edge zod constructs
   (unions, refinements, effects) may translate in surprising ways — the ancestor-optional rule
   ("optional at any level along the path") papers over this but should be tested against real
   nesting.

4. **silent omission trades away a safety net.** an optional field that's *absent for the wrong
   reason* (typo'd path → not-found) resolves silently. required fields keep their guard, so this
   is bounded, but it's a genuine tradeoff: optionality buys tolerance at the cost of "did I mean
   to be missing?" detectability.
