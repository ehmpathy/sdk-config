# c3 — a uni-time in-memory cache is refused at compile (sharp × criti)

## narrative

an adopter bumps sdk-config but leaves `simple-in-memory-cache@0.4.0`. what tsc says depends on which `@ehmpathy/uni-time` the cache resolves. where `UniDuration` resolves (uni-time <= 1.9.x), tsc fails at the `cache:` line: the contract hands `set` an `IsoDuration`, which may be words (`'PT5M'`), and a uni-time `expiration` cannot hold them. where uni-time floats to 1.10.0 — which no longer exports `UniDuration` — the cache's `expiration` collapses to `any` under `skipLibCheck`, and tsc accepts it. either way no runtime break: sdk-config passes no expiration. the readme and the pr body name the recommended floor: `simple-in-memory-cache` >= 0.4.2.

## fail-safe

- where it refuses: fast (compile time) and loud (tsc error at the adopter's `genGetConfig` call).
- where it accepts (`any`): safe anyway — sdk-config never passes an `expiration`, so a uni-time cache fills correctly at runtime (`[case8] [t2]` proves the fill runs past the type gate).
- teaches the fix: the readme names the floor (`>= 0.4.2`); the pr body names the contract change.
- the tsc message itself does not name the floor — the readme carries it.

## timeline

```
given an adopter on simple-in-memory-cache 0.4.0
when [t0] it bumps sdk-config to 0.4.0, and its uni-time resolves UniDuration (<= 1.9.x)
then tsc refuses the cache — IsoDurationWords is not assignable to its expiration
when [t0'] it bumps sdk-config to 0.4.0, and its uni-time floats to 1.10.0
then tsc accepts the cache (expiration is any)
  and the fill runs — sdk-config passes no expiration
when [t1] it bumps simple-in-memory-cache to 0.4.2+
then tsc is clean
```
