# c4 — an async dynamodb cache fails silent (sharp × criti)

## narrative

an adopter that shares cache across lambdas reaches for `@ehmpathy/simple-dynamodb-cache@1.0.8`, the latest. tsc accepts it: 1.0.8 imports `SimpleAsyncCache` from with-simple-cache, a name 0.17 no longer exports, so under `skipLibCheck` its cache type collapses to `any` (probe: a scratch pnpm install of 1.0.8 + with-simple-cache 0.17.3 assigns `createCache(...)` to `SimpleCacheSync<unknown>` clean). at runtime it fails silent: it is an **async** cache, and `genGetConfig` wraps the fill with the sync `withSimpleCache` — `get` returns a promise that reads as a hit, and `getConfig()` resolves `undefined` with 0 supplier calls. this was true on 0.3.0 as well (`get`'s promise fits `unknown`). the readme says async caches are not supported; a dream tracks async support.

## fail-safe

- none at compile time, before or after this change — `unknown` absorbs a promise, and the type gate cannot refuse async caches without refusing the standard `createCache()`.
- the readme ⚠️ is the only guard until the async dream (`.dream/v2026_11_08.fix.sdk-config-cache-wrapper-async-safe.md`) lands. the pr body names it.
- deliberately not pinned by a test: a test that asserts `getConfig()` → `undefined` would enshrine the defect the dream removes. evidence lives in the F7 probe instead.

## timeline

```
given an adopter on @ehmpathy/simple-dynamodb-cache 1.0.8
when [t0] it passes createCache({ dynamodbTableName, expiration }) to genGetConfig
then tsc accepts the cache (its type collapses to any)
when [t1] it calls getConfig()
then the config resolves undefined, with no supplier call (pre-extant)
  and the readme names async caches as unsupported
```
