# vision: sdk-config on the decycled with-simple-cache iso-time line

## the outcome world

sdk-config's `cache` input binds `with-simple-cache@0.17.3`'s `SimpleCacheSync<unknown>`. an adopter:

- passes `createCache({ expiration: { minutes: 5 } })` from `simple-in-memory-cache@0.4.2+` to `genGetConfig`. it typechecks and fills.
- drops any `with-simple-cache` override aimed at sdk-config. sdk-config already resolves 0.17.3.
- drops its `.dpdmrc.yaml` exclusion `with-simple-cache@0.15.3`. sdk-config's path was the one that carried 0.15.3 into the app graph.

| | before (sdk-config 0.3.0) | after (next minor) |
|---|---|---|
| with-simple-cache in prod graph | 0.15.3 — 2 dpdm cycles | 0.17.3 — 0 cycles |
| cache contract | `SimpleSyncCache` (uni-time) | `SimpleCacheSync` (iso-time); a uni-time cache is refused only where its `UniDuration` resolves |
| uni-time in prod graph | `@ehmpathy/uni-time` via 0.15.3 | absent |
| adopter workaround (svc-home-services) | dpdm exclusion `with-simple-cache@0.15.3` + pin `simple-in-memory-cache@0.4.0` | none |

aha: the adopter deletes its workarounds and adds none.

## mental model

"sdk-config moved its cache contract from uni-time to iso-time, the same move with-simple-cache made." the adopter's word is "cache"; ours is `SimpleCacheSync`.

## evaluation

- pro: adopter workarounds removed; uni-time leaves sdk-config's prod graph.
- con: a breaking type change for uni-time caches — where their `UniDuration` resolves (uni-time <= 1.9.x). where uni-time floats to 1.10.0, the cache's `expiration` is `any` and tsc accepts it. no runtime break either way: sdk-config passes no expiration. sdk-config is 0.x, so it owes a minor bump (0.3.0 → 0.4.0).
- edge: `@ehmpathy/simple-dynamodb-cache@1.0.8` (latest) is accepted by tsc — it imports `SimpleAsyncCache`, which 0.17 no longer exports, so its type collapses to `any` (scratch-install probe). it fails silent at runtime: it is async, and `genGetConfig` wraps with the sync `withSimpleCache` (pre-extant, true on 0.3.0 too). the readme says async caches are unsupported; dreams track both.

## groundwork

### external research

- `npm view with-simple-cache@0.17.3 dependencies` — `iso-time 1.11.7`, `simple-in-memory-cache 0.4.2`, no uni-time.
- `npm view with-simple-cache@0.15.3 dependencies` — `@ehmpathy/uni-time ^1.7.4`.
- `npm view simple-in-memory-cache@{0.4.0,0.4.2,0.5.1} dependencies` — 0.4.0 uni-time; 0.4.2 and 0.5.1 `iso-time ^1.11.7`.
- `npm view @ehmpathy/simple-dynamodb-cache` — latest 1.0.8; `dist/cache.d.ts:25` types `expiration?: UniDuration | null`.
- `simple-in-memory-cache@0.4.2` `dist/cache.d.ts:1,5` types `expiration?: IsoDuration | null`; both 0.4.2 and 0.5.1 are clamped by `genGetConfig.integration.test.ts` `[case8]`.
- dpdm 3.14.0 over the installed dists: 0.15.3 reports 2 cycles (`getCacheFromCacheChoiceOrFromForKeyArgs` ↔ `withExtendableCacheAsync` ↔ `withSimpleCacheAsync`); 0.17.3 reports none.

- `ahbode/svc-home-services` @ origin/main: `.dpdmrc.yaml:23-29` excludes `with-simple-cache@0.15.3` and blames sdk-config@0.2.3; `package.json:78,81` pins `sdk-config 0.2.3` + `simple-in-memory-cache 0.4.0`; no with-simple-cache override. its lockfile also holds with-simple-cache 0.15.1 / 0.16.1 / 0.17.0 via dev tools (`declastruct-github`, `declastruct-aws`) — outside the app import graph dpdm walks, and outside this wish.

### internal research

- contract: `src/domain.operations/genGetConfig.ts:2,20` — the one import site; `cache: SimpleSyncCache<unknown>`.
- 0.17.3 renames the type: `dist/domain.objects/SimpleCache.d.ts` exports `SimpleCacheSync<T, TCondition = never>`; `set` options `expiration?: IsoDuration | null`.
- surface: `src/contract/sdk.ts` exports no cache type — the change rides the `genGetConfig` input only.
- release: `.github/actions/please-release/action.yml:179-186` — `^break(...)` → major, `^feat(...)` → minor, all else patch. ⚠️ `feat!:` would miss the regex and mint a patch; `commitlint.config.js` (`subject-exclamation-mark: never`) refuses it first.
- finding: `@ehmpathy/uni-time@1.10.0` no longer exports `UniDuration`. with `skipLibCheck`, any type that names it collapses to `any` — the old contract's `expiration`, and a real `simple-in-memory-cache@0.4.0` cache's too (probe: 0.4.0 + uni-time 1.10.0 → accepted by the new contract). so "an iso cache compiles" cannot tell old from new; the `[case8] [t2]` fixture refusal can, and a real uni-time cache is refused only where `UniDuration` resolves.

## what is awkward?

- the break is one-directional: iso-time caches fit the new contract, uni-time caches do not. adopters on `simple-dynamodb-cache` wait on an upstream release.
- the old contract was silently `any` in fresh installs. the new contract is stricter than what adopters saw in practice.
