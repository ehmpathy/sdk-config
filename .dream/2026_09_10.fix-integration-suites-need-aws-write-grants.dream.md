## .the gap, precisely

two suites seed their own aws fixture in `beforeAll` and tear it down in `afterAll`.
**every one of those four calls is denied**, and every denial names a write action:

| suite | call | denied action |
|---|---|---|
| `genSdkConfigSupplierAwsParameterStore.integration.test.ts:46` | `PutParameterCommand` | `ssm:PutParameter` |
| `…ParameterStore…:58` | `DeleteParameterCommand` | `ssm:DeleteParameter` |
| `genSdkConfigSupplierAwsSecretsManager.integration.test.ts:46` | `CreateSecretCommand` | `secretsmanager:CreateSecret` |
| `…SecretsManager…:56` | `DeleteSecretCommand` | `secretsmanager:DeleteSecret` |

verbatim, from the run:

```
AccessDeniedException: User: arn:aws:sts::261599400667:assumed-role/ahbode-camp-grove-role/i-0642a53a180f22a32
  is not authorized to perform: ssm:PutParameter
  on resource: arn:aws:ssm:us-east-1:261599400667:parameter/ehmpathy/test/sdk-config/integration-test-<uuid>
  because no identity-based policy allows the ssm:PutParameter action
```

🔴 **it is a grant gap, never an expiry.** *"no identity-based policy allows"* is how
aws phrases an absent permission; an expired token reads `ExpiredTokenException`. so a
re-`keyrack unlock` cannot fix it, and the run above had a fresh unlock
(`keyrack: unlocked ehmpath/test`).

⇒ **the READ grants exist and the WRITE grants do not.** proof, from the same session:
`genGetConfig.integration.test.ts` passes **58/58** against live aws, and it reads real
params. so the role is provisioned as a reader, and any suite that must author its own
fixture is dead on arrival.

### the second-order failure it produces

the denial does not merely fail the setup — it makes each suite report an assertion
failure that **points at the wrong subject**, because the fixture the test then reads
was never created:

- param-store `[case1]` → `SupplyAbsentError: parameter not found` (correct behavior,
  wrong cause — the param is absent because the seed was refused)
- secrets-manager `[case3]` → `Expected SupplyAbsentError, received SupplyDeniedError`

⇒ whoever opens only the assertion sees a supplier defect. the cause is four frames up,
in a `beforeAll`.

## .the shape of the fix

grant the test role the four write actions, scoped to the test prefix it already reads:

```
ssm:PutParameter, ssm:DeleteParameter
  → arn:aws:ssm:us-east-1:*:parameter/ehmpathy/test/sdk-config/*

secretsmanager:CreateSecret, secretsmanager:DeleteSecret
  → ehmpathy/test/sdk-config/*
```

both suites already scope their fixtures under
`ehmpathy/test/sdk-config/integration-test-<uuid>`, so the grant needs no wildcard wider
than that prefix.

🔴 **and the acceptance suites need a second prefix, which the amendment adds.** they seed under
the **derived** path, which this behavior widens from three segments to four:

```
ssm:PutParameter, ssm:DeleteParameter
  → arn:aws:ssm:us-east-1:*:parameter/test-org/test-svc/*      ← NEW, four-segment
```

⚠️ **grant it by prefix, never by the literal path.** the fixture's org comes from
`src/__test_assets__/config/test.yml`'s `organization` field, so a literal grant re-breaks the
moment that fixture is edited.

🟡 the alternative — hoist the fixtures to a provisioned, pre-seeded param the reader
role can already see — trades a grant for a shared mutable fixture, and
`rule.require.hermetic-tests` argues against it.
